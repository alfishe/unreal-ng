# ATM450 frame length: the system ROM's frame-timing protection

**Created:** 2026-10-02 · **Status:** implemented on branch `atm450` · part of
[requirements.md](requirements.md) (R1 timing, OQ-11)

## Summary

The ATM Turbo 2 v4.50 system ROM (`data/rom/atm1.rom`, BIOS 1.03rs) measures the
length of a frame before it starts CP/M and, on every key press afterwards, checks
the measurement against a window calibrated on the real board. Outside the window
it **corrupts input on purpose**: some keys arrive as the next scan code ("DIR" →
"DKR", "R" → "4", space → "Z") and some presses increment a random byte of memory.
Every emulator we know ships the ATM 4.50 with a 69 888 T frame (312 × 224), which
measures outside the window. unreal-ng's ATM450 therefore uses a **308-line frame of
224 T = 68 992 T**, which measures inside it.

There is no primary hardware source for the 4.50 raster (the sync is generated by the
protected PLM 1556ХЛ8, whose firmware is not public, and the board manual gives no line
count). The frame length is **inferred from the ROM's own calibration**; see
"Evidence" and "What is not known".

## The two ROM protections

Both live in the system ROM page 0 and both depend on timing the board's PLM produces.
Addresses below are in `atm1.rom` page 0; labels follow the commented BIOS 1.03
disassembly `CPM-ATM dizasm.TXT`
(<http://atmturbo.nedopc.com/inf/books/nedopc/CPM_ATM_dizasm.zip>), whose layout
matches 1.03rs for these routines.

1. **Z key** (`l1fba`, `l201e`-`l2033`): after `HALT` and a fixed delay the ROM samples
   the PLM's Z signal (`IN A,(#FE)` bit 7) 16 times and XOR-decrypts its CP/M loader
   (`#22B3` → `#D400`) with the result. Implemented as the INT-relative PAL marker
   windows in `PortDecoder_ATM450::PalMarker` (requirements R2 arm 6, OQ-9).
2. **Frame measure** - this document.

### Frame measure

`l1fff` (called from `l1fba` before CP/M starts):

```
l1fff  call l1fe6        ; IM 2, vector #F9FF -> #201C (SCF; RET), HL = 1
       ei
       halt              ; INT edge
       ld b,#14
       djnz $            ; fixed delay
       or a              ; carry clear
       ei
l200a  inc hl            ; 6 T
       jr nc,l200a       ; 12 T  -> one iteration = 18 T
       ld (#5f74),hl     ; iterations until the next INT
```

So `#5F74` (16 bit) ≈ (frame T − ~303 T of INT acknowledge, handler and delay) / 18 + 1.

`l1500` (keyboard interrupt, right after a new key code is stored in the key buffer):

```
       ld a,(#5f74)      ; low byte of the measure
       bit 4,(ix+#35)    ; ix = #5F40: (ix+#35) = #5F75 = high byte; bit 4 = measure >= #1000
       jr z,$+4
       add a,#08
       sub #e6
       cp #07
       ret c             ; low byte in #E6..#EC: the board is genuine, nothing happens
       ld a,r
       and #78
       jr nz,l1536
       ld hl,(#5f5c)     ; R & #78 = 0: HL = the frame counter (a "random" address)
l1536  cp #10
       ret nc
       inc (hl)          ; R & #78 = #08: HL = the key buffer slot -> key code + 1
                         ; R & #78 = 0   : a random byte of memory + 1
       ret
```

The scan code of a key is `row + 8 * bit` (rows `#FEFE`..`#7FFE`), so "+1" is the key in
the same column of the next matrix row - exactly the observed I → K, A → Q, R → 4,
space → Z.

## Evidence

Measured with the CP/M boot test (`ATM450Boot_Test.CpmBootsFromSystemDiskAndListsIt`,
keys logged at the ROM's store `#1514` and its code-to-character lookup `#15B4`):

| Frame (T) | Lines × T | `#5F74` | In window | Typed keys |
|---|---|---|---|---|
| 69 888 | 312 × 224 (UnrealSpeccy `PRESET.ATM1_2_3.5MHz`, ZXMAK2 `UlaAtm450`) | `#0F1C` | no | corrupted (stored `07`, converted `08`) |
| 68 992 | 308 × 224 | `#0EEA` | yes | clean |
| 73 600 | - | `#0FEA` | yes | clean |
| 71 680 | 320 × 224 (Pentagon) | `#0F7E` (computed) | no | - |

The emulated keyboard was probed to rule out an emulation fault: every row read returned
the current matrix state, the keyboard interrupt ran once per frame, and the code the
ROM stored was correct - the "+1" was applied by the ROM itself at `#1539`.

The window accepts measures `#?EE6`..`#?EEC` (or `#?DE`..`#?E4` with bit 12 set), i.e.
a frame of about **68 940 - 69 045 T** or **73 550 - 73 650 T** at 3.5 MHz. A
TV-compatible raster of 224 T lines fits the first range with **308 lines**
(19.71 ms, 50.73 Hz); nothing in the second range is a plausible PAL raster.

## The model in unreal-ng

- Frame **308 × 224 = 68 992 T**, ATM450 only (`Config::ApplyModelTimingDefaults`,
  `data/configs/atm450/unreal.ini`). ATM710 / ATM3 keep 312 lines.
- The 4 missing lines are taken from the **vertical blank before the visible area**
  (24 → 20 sync + blank lines): the visible 288 lines, the framebuffer and every
  mode's window stay identical to 7.10 (`Screen::GetTimingDescriptor`,
  `ScreenAtm::Draw`, `AtmVideoMapper`).
- INT moves 4 lines earlier with them: `intstart` 1756 → **860**, so the
  INT-to-first-paper distance stays **14 395 T** (UnrealSpeccy / DDp) and the
  INT-relative Z windows are untouched.

## What is not known

- Which lines the real PLM drops (blank, border or sync) and the real INT-to-paper
  distance on a 4.50 board. Only the total frame length is constrained by the ROM.
- Whether the real board is 308 × 224 or has another split giving a frame in the same
  window (e.g. per-line CPU waits on a 312-line raster: ~2.8 T per line). Both measure
  the same in the ROM; they differ only for raster-timed effects.
- A logic-analyzer capture of VS / INT on a 4.50 board, or the PLM 1556ХЛ8 equations,
  would settle it.
