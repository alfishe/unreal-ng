# Keyboard 3D models: requirements

## 1. Problem

The AR / VR integration (the UE plugin of [ue-integration-design.md](../2026-09-19-unrealengine-integration/ue-integration-design.md),
later Apple AR) puts an emulated machine on a desk in 3D: a monitor whose screen is the emulator's frame, and the
machine's own keyboard whose keys the user presses with tracked hands or a controller. The plugin plan has
`Content/Meshes/ (sample monitor, keyboard, ...)` and a `ZXKeyComponent` per key, but no keyboard model exists.

Hand-modelling about 15 keyboards is weeks of work, and every fix (a key width, a colour, a legend) must then be
redone by hand in each format. POC 031 already holds every keyboard as data, measured and checked against photos.
A script that builds the 3D model from that data makes a keyboard reproducible, correctable in one place and
exportable to any format.

## 2. Goals

| # | Goal |
|---|---|
| G1 | A photoreal 3D model of each keyboard of [keyboards.md](keyboards.md), at real scale, recognisable as the real machine next to its photos |
| G2 | Generated by scripts from the POC 031 data (`keyboards/<id>.py`) plus 3D-only data (heights, profiles); no hand edits in a DCC tool |
| G3 | Every key a separate, pressable node that carries what it presses (the ZX matrix keys, the PC key, or the machine's own line), the same ids as `keys.json` |
| G4 | Exports to the formats the consumers need (glTF / GLB first, USD / USDZ, FBX, OBJ, STL) from the same build |
| G5 | Game-ready: triangle and texture budgets that run on standalone Quest, LODs, PBR materials that look right in UE, Blender, three.js and Apple Quick Look |

## 3. Consumers and use cases

| Consumer | Use |
|---|---|
| UE plugin (`UnrealNG`, UE 5.3+, 4.27) | the keyboard actor: a static case mesh, one key component per key node, the press animated by the emulator's key state and by hand or controller collision; OpenXR on PC VR and Quest |
| Unity (2022 LTS+, FBX native, glTF through glTFast) | the same keyboard as a prefab: a mesh per key, the key properties read on import, XR Interaction Toolkit for the hands; first priority with UE |
| Apple AR (USDZ, Quick Look / RealityKit) | a keyboard placed on a real desk; later live, through the iOS host ([2026-09-19-ios-integration](../2026-09-19-ios-integration/)) |
| Web (three.js / model-viewer) | a gallery and a preview of the models |
| Offline renders | marketing shots, the README, a check against the photos |
| 3D print (STL) | a scale model; not a goal, but free from the same geometry |

Use cases:
1. A VR user sits at a desk with a 48K; they press a rubber key with a fingertip; the emulator sees the key; the key
   goes down 2 mm and comes back.
2. A program presses keys through the emulator (an autotyped LOAD ""); the model's keys move with the emulator's
   matrix state.
3. The owner fixes the width of a Pentagon key in `pentagon2plus.py`; the SVG, the keys JSON and every 3D export are
   rebuilt by one command.

## 4. Functional requirements

### 4.1 Geometry

- FR1 Real scale in metres in the exports (the data is in mm). The footprint of the case and every key rectangle
  match the POC 031 data exactly: the 2D picture is the model's top view.
- FR2 The case is modelled all round: top, sides, front, rear, underside with feet; the features of each case of
  [keyboards.md](keyboards.md) (the 48K hump and plate, the 128's heatsink fins, the Amstrad castellated rear and
  Datacorder or drive, the Next's wedge and rainbow, the Quorum's vent field).
- FR3 Keycaps by **cap family** (data-model.md §3): the profile (flat, cylindrical, spherical dish, sculpted rows),
  the skirt draft, the top face inset and the corner radii are parameters of the family; a keyboard picks a family
  and may override a parameter. L-shaped ENTER keys and two-row keys are first-class shapes.
- FR4 Each key has a travel (rubber ≈ 1.5–2 mm, mechanical ≈ 3.5–4 mm, membrane caps per family) and its pivot at the
  centre of its top face, so that a consumer moves a key with one translation along the key's own down axis.
- FR5 The keys that the 2D data marks as twins (two CAPS SHIFT, two SYMBOL SHIFT on the 58-key boards; the Quorum's
  FIRE on 0) are separate nodes with the same mapping.

### 4.2 Legends and colours

- FR6 Every legend of the 2D data appears on the 3D cap: the same text, role, face, size, colour and placement, on
  the top face or on the front slope where the 2D data puts it (the Pentagon 2+'s E-mode words, the Quorum's BASIC
  words). Text is converted to outlines from the same fonts as POC 031 (`svgkit.py`).
- FR7 The colours are the POC 031 colours (sampled from the owner's photos and neutral-light photos), used as base
  colours of PBR materials; no colour is invented in the 3D project. A new colour comes with a source.
- FR8 Case print (logos, badges, rainbow stripes) and moulded logos (the 48K's "sinclair", the Scorpion's plaque)
  are reproduced: printed ones as decals or texture, moulded ones as relief geometry or a normal map.

### 4.3 Key semantics

- FR9 Every key node carries, as custom properties (glTF `extras`, USD `customData`, FBX user properties):
  `id`, `label`, `zx` (the matrix keys, `["CS","1"]` for EDIT), `pc` (the PC key), `line` (the Quorum's `#7E:4Fh`,
  `NMI`, `RESET`), `travel_mm`, `keyboard` (the keyboard id) and `models` (the emulator's model short names).
- FR10 A key's collision shape (a box or a convex hull of the cap) is exported for VR hand interaction, named
  `UCX_<node>` for UE's import.
- FR11 The keys JSON of POC 031 stays the one source of truth for ids and mappings; the 3D build checks that its key
  set equals the JSON's (the same ids, the same mappings, no key missing or extra).

### 4.4 Exports

- FR12 Formats, in priority order (owner 2026-10-20): **FBX** and **GLB / glTF 2.0** first (UE 5.3+ and 4.27,
  Unity, three.js, Blender), then **USDZ / USD** (Apple AR), **OBJ + MTL**, **STL** (one solid per part). Optional: `.blend` of the built scene.
- FR13 Each export of a keyboard holds the case node, the key nodes under a `keys` group, the legend meshes parented
  to their keys, the collision shapes, and the LODs (LOD0 full, LOD1 ≈ 50 %, LOD2 ≈ 15 %).
- FR14 Textures: base colour, ORM (occlusion / roughness / metallic) and normal maps, power-of-two sizes, one atlas
  per keyboard where a consumer needs it (Quest).

### 4.5 Build

- FR15 One command builds one keyboard or all (`build.py [ids] [--formats glb,usdz,...] [--lod ...]`), headless,
  from the data in the repository; the result is byte-reproducible for the same inputs and tool version.
- FR16 A preview render of each keyboard: the top view (to compare with the POC 031 picture), a three-quarter view
  and a side view, in a neutral studio light; a sheet per keyboard like POC 031's atlas.

## 5. Non-functional requirements

| # | Requirement |
|---|---|
| NFR1 | Budget per keyboard at LOD0 (proposed, to be confirmed on a Quest): ≤ 150 k triangles (58-key board), ≤ 250 k (Quorum, PC 101-key); ≤ 4 texture sets of 2048²; LOD2 ≤ 15 k triangles. Quest standalone target: 72–90 Hz with the monitor and the room |
| NFR2 | Materials look the same in UE (Lumen and baked), Blender Cycles / EEVEE, three.js and Quick Look: metal-rough PBR only, no engine-specific shader in the export |
| NFR3 | The build runs on macOS (dev), Linux (CI) and Windows; Blender 5.2 LTS pinned; no network at build time |
| NFR4 | Deterministic: the same inputs give the same files (no random seeds without a fixed seed, no timestamps in the files) |
| NFR5 | Every 3D-only number (a height, a profile radius, a travel) has a source or is marked UNVERIFIED in the data, as in POC 031 |
| NFR6 | Licences: none to ask (owner: no licence questions); fonts are the system fonts POC 031 uses, converted to outlines, not shipped as font files |

## 6. Scene conventions

| Item | Convention |
|---|---|
| Units | metres in the exports, millimetres in the data |
| Axes | glTF: Y up, the keyboard's front toward +Z; the exporter converts for FBX / USD (Z up in UE, Y up in USD for Quick Look) |
| Origin | the case's bottom plane, at the centre of its footprint; the case sits on the floor plane y = 0 |
| Key pivot | the centre of the key's top face at rest; the press is a translation along the key's local −Y |
| Naming | `kbd_<id>` root, `case`, `keys/key_<keyid>` (the `keys.json` id), `legend_<keyid>_<role>_<n>`, `UCX_key_<keyid>`, `case_LOD1` ... |
| Materials | `<keyboard>_<part>_<colour>`, e.g. `zx48k_rubber_blue_grey`; one material per real material, not per key |

## 7. Non-goals

- No animation clips in the files beyond the key travel (a consumer drives the keys).
- No interior (boards, chips) except where it shows through a case: the +2's Datacorder window may show a cassette
  well, nothing else.
- No physics tuning beyond collision shapes.
- No changes to the OSD or the SVG pipeline of POC 031; the 3D project only reads its data and adds 3D fields.
- No dirt, wear or ageing (owner rule).

## 8. Acceptance

- Each keyboard of [keyboards.md](keyboards.md) in GLB, USDZ, FBX, OBJ, STL; the owner judges each as authentic and
  photoreal next to its reference photos, or names what is wrong.
- The key set check (FR11) passes for every keyboard; every key has a mapping.
- The GLB files pass the Khronos glTF validator with no errors; the FBX and GLB import into Unity with their key
  properties; the FBX imports into UE 5.3 with its
  collisions and LODs; the USDZ opens in Quick Look.
- The top render overlaid on the POC 031 picture: every key rectangle within 0.5 mm.
- The budgets of NFR1 hold.

   the deliverable; how a consumer visualises them does not matter. FBX and GLB are checked first (UE import, Unity

2. **Legends**: geometry (outlined text extruded 0.05 mm, sharp at any distance, more triangles) or baked into a

5. **Repository place**: `tools/keyboard3d/` (a tool) or `assets/keyboards/` with the generated files committed
   (GLB / USDZ are tens of MB per keyboard)?
