The on-screen keyboard a pad opens with `osd.keyboard` shows the keyboard of the machine being emulated, not a
generic 48K: a Pentagon gets the Soviet mechanical keyboard it was built with, a +3 its black Amstrad case, a
ZX-Evo a PS/2 PC keyboard with a switch to the ZX matrix. This POC answers whether every model of the emulator can
have a photorealistic vector picture of its own keyboard, built from verified references, with every key mapped to
what the machine reads, before the overlay is built into unreal-qt.

## Phases

| Phase | Style | What |
|:--|:--|:--|
| 1 | `photo` | photorealistic vector: real colours, lit materials, soft shadows |
| 2 | `schematic` | the same keyboards as clean vector diagrams: flat, outlined, legible at a glance |
| 3 | `hybrid` | a mix of the two plus a hints layer (what a combo key does); the legends grouped by role for the mode legends that matter now |

One model per keyboard feeds every style (`design.md`): the geometry, legends and mapping are data, a style only
draws them. Every SVG has the same named layers (`case`, `caps`, `highlights`, `legends`, `hints`), so a hybrid takes each layer
from another style and Qt can draw a layer alone (`QSvgRenderer::render(painter, elementId)`).

## Goals

1. Which keyboard each of the 21 models had (`Config::mem_model`): the case or the separate keyboard, the key
   count and layout, the colours, the keycap shapes and the legends, each from sources (photos, manuals,
   schematics, the owner's local zx-spectrum data collection).
2. Whether one vector generator can draw all of them photorealistically: the materials (rubber, hard plastic,
   Soviet mechanical caps, PC caps), the lighting and the legends as SVG only, no bitmaps, within what
   `QSvgRenderer` draws.
3. Whether every key maps to the machine: the ZX 8x5 matrix position (half-row, bit) and the shift it needs, or for
   a PC keyboard its PC key (the scan code the machine's keyboard controller reads).

## Requirements

- Every model of `Config::mem_model` (21) gets a keyboard; models that share one say so (128K and +, +2A and +3
  keyboards, the three Scorpion variants).
- The PC-keyboard clones (ATM-Turbo, ZX-Evo, TS-Conf, Sprinter, Phoenix and others found to be such) get both:
  the PC keyboard of their era and the 40-key ZX matrix, switchable (owner 2026-10-19). ATM-Turbo 512 v4.50 had
  no PC keyboard (the controller came with the 7.00 boards, NedoPC atmdscr.htm), so it gets the matrix only.
  Three PC keyboards from one generator (`keyboards/pc.py`, owner 2026-10-20): the XT 83-key for the ATM-Turbo 2+
  (its first XT firmware) and the KAY, the AT 101-key for the ATM-Turbo 2+ (AT firmware) and the Sprinter, the PS/2
  104-key Russian clone for the ZX-Evo, TS-Conf and ZXM-Phoenix.
- Pentagon: the Soviet 40-key mechanical keyboard of the early 1990s builds (owner 2026-10-19).
- Where the keyboard is the computer's case (48K, 48K+, 128K, +2, +2A, +3, Next), the picture is the case's top.
- Vector only, generated by a script from data, reproducible. Qt's `QSvgRenderer` draws SVG Tiny 1.2: gradients,
  opacity and paths, no filters (no blur, no drop shadow), so shading, shadows and highlights are layered
  gradient shapes.
- Each key: its matrix or PC key, its legends (main, keyword, symbol, the colour of each), its rectangle for the
  overlay's cursor and its pressed state.
- Each picture states its sources in a `provenance.json`; a claim without a source is marked as one
  (a comment or a forum post alone is not proof).

## Constraints

- POC code only (`tools/poc/031-authentic-osd-keyboards/`): nothing in `core/` or the apps changes.
- Build output and the per-mode renders go to `scratch/2026-10-19-poc-031/` (git-ignored). The generator, the data,
  the generated SVGs, the atlas sheets, the references with their photos and the reports are committed (owner
  2026-10-19).
- No embedded photos: the pictures are drawn, the photos are references. A printed mark may be traced from a photo
  into vector outlines (`trace.py`) when no font matches it (the Profi badge, owner 2026-10-20).

## Acceptance criteria

- A gallery (`gallery.html`) shows all 21 models; the owner judges each picture as authentic and photorealistic,
  or names what is wrong.
- Every key of every picture has a mapping; a script check finds no key without one and no matrix position
  without a key (where the machine has one).
- Each SVG renders the same in Qt's `QSvgRenderer` and in a browser; the check renders both and compares.
- Expected: about 12 distinct keyboards for the 21 models; the PC clones share 2 or 3 PC keyboards plus the matrix.

## In the app

The pictures are the app's on-screen keyboard (View → On-screen Keyboard, the `osd.keyboard` action; owner
2026-10-20: a window of its own, a switch between a model's keyboards): `unreal-qt/src/osdkeyboard/` reads
`data/controllers/keyboards/` (this POC's output) and posts a click as the matrix keys or the PC key of the key
(docs/features/keyboard.md "On-screen keyboard"). A second switch picks the style for every model (photo, schematic, hybrid;
`osd_keyboard_style` on every automation plane, the `osd.keyboard_style` action).

## Phases 2 and 3 (2026-10-23)

- `styles/schematic.py`: every keyboard as a diagram from the same model; `styles/hybrid.py`: the photo's caps on
  the schematic's case with the hints layer (design.md). All 63 SVGs (21 keyboards x 3 styles) pass the check:
  every key mapped, Qt's QSvgRenderer and rsvg alike (the largest mean difference 1.67 of 255, the 128's schematic:
  its many hairlines; no pixel far off).
- The legends layer is grouped by role in every style. The app dims the roles that do not matter now: while Symbol
  Shift alone is held, every mode legend but the symbols (`keyword`, `extend`, `extend-shift`, `graphic`, `colour`,
  `cyrillic`) is drawn at 30 % (`OsdKeyboardView::setDimmed`). Not built: dimming by the ROM's mode (keywords in
  K mode, the extend legends in E mode): the mode lives in the guest's system variables, which a game may reuse, and
  which role it brings forward differs per keyboard (the 48K's red words below the key need Extend Mode, the 128's
  need none).

|---|---|

| `atlas/<id>.<style>.atlas.png` | one sheet per keyboard and style with all those modes |
| `gallery.html` | all models side by side |
